# OpenRouter Free Marking Provider Design

**Date:** 2026-08-08

## Goal

Replace the unavailable local Ollama vision model with OpenRouter while preserving the existing
two-stage OCR and provisional-grading pipeline. All inference must use OpenRouter's free-model
router, and transient failures must remain queued with persistent exponential retry timing.

## Scope

This change covers the model-provider adapter, provider configuration, database-backed retry
state, worker selection behavior, error classification, and automated tests. It does not change
the marking prompts, output schemas, tutor-review requirement, student submission flow, or media
lifecycle.

Partial OCR results will not be persisted in this iteration. If a later grading call fails, the
next attempt repeats OCR for every submitted page.

## Provider Architecture

Add an `OpenRouterVisionOCR` adapter that implements the existing `VisionOCR` protocol:

- `transcribe(image: bytes) -> OCRResult`
- `propose_grade(transcription, solution_images, maximum) -> ProposedGrade`

`LocalVisionPipeline` will continue to depend on that protocol, so PDF rendering, Telegram media
download, result aggregation, and marking decisions remain provider-independent. Runtime wiring
will construct `OpenRouterVisionOCR` instead of `OllamaVisionOCR`.

The adapter will call:

```text
POST https://openrouter.ai/api/v1/chat/completions
```

using `Authorization: Bearer <key>`. The model will be fixed to `openrouter/free`, which
routes only among currently available free models. OpenRouter will filter candidates based on the
request's required capabilities, including image input and structured output.

The implementation will use the existing `httpx` dependency rather than adding an SDK.

## Configuration

Add these settings under the existing `AMATH_` environment prefix:

- `AMATH_OPENROUTER_API_KEY`: required to run the polling bot and never committed to the repository.
- `AMATH_OPENROUTER_URL`: defaults to `https://openrouter.ai/api/v1`.

The provider adapter will use `openrouter/free` as a code-level constant rather than accepting an
arbitrary model setting. This preserves the strict zero-cost requirement and prevents an accidental
deployment override from selecting a paid model.

Docker Compose will pass the API key through from the deployment environment. The obsolete Ollama
runtime settings will be removed once no production code references them.

Startup will reject a missing OpenRouter API key before polling begins. This avoids repeatedly
claiming queued work when the provider cannot be called.

## Request and Response Contract

Both OpenRouter calls remain non-streaming and use temperature zero.

Images will be sent as multipart message content with base64 data URLs:

```json
{
  "type": "image_url",
  "image_url": {
    "url": "data:image/png;base64,..."
  }
}
```

The OCR request contains the existing OCR prompt followed by one submitted page. The grading
request contains the existing grading prompt and all rendered published-solution pages.

Each request will set `response_format.type` to `json_schema`, enable strict mode, and supply the
schema generated by `OCRResult.model_json_schema()` or `ProposedGrade.model_json_schema()`.
Provider routing will require support for the parameters used by the request, preventing a route
that silently omits structured-output enforcement.

Responses will still undergo local Pydantic validation. Grading responses will retain all current
post-validation invariants:

- awarded totals cannot exceed the question maximum;
- decision maxima cannot exceed the question maximum in aggregate;
- awarded marks cannot exceed their decision maximum;
- awarded marks require cited student lines; and
- the application recalculates and replaces the provider-reported total.

Schema compliance does not prove semantic accuracy. Every produced grade therefore remains
flagged for mandatory tutor approval.

## Database-Backed Retry State

Extend `submission_attempts` with:

- `marking_attempts`: non-negative integer, default `0`;
- `marking_retry_at`: nullable timezone-aware timestamp, indexed;
- `marking_last_error`: nullable bounded string containing a safe diagnostic summary.

When a student submits an attempt, it enters `queued` with no retry delay. The worker will poll
every three seconds and select only queued attempts for which `marking_retry_at` is null or is not
later than the current time.

Before a provider attempt, the row becomes `processing`. On a retryable failure, it returns to
`queued`, `marking_attempts` increments, `marking_last_error` is updated, and
`marking_retry_at` is calculated from this schedule:

| Failed attempt | Delay before next attempt |
|---:|---:|
| 1 | 3 seconds |
| 2 | 10 seconds |
| 3 | 30 seconds |
| 4 | 30 seconds |
| 5 and later | 60 seconds |

Retries continue indefinitely at 60-second intervals. On successful processing, retry time and
last error are cleared. The attempt count may be retained for operational history.

The existing `FOR UPDATE SKIP LOCKED` claim behavior remains. The scheduler continues to allow at
most one local marking-job instance at a time.

## Error Handling

Retryable provider failures include:

- rate limiting;
- free-model unavailability;
- provider 5xx responses;
- timeouts and transport failures;
- malformed, refused, or schema-invalid model output; and
- failures of the existing grading invariants.

These failures leave the submission queued and use the retry schedule above.

Configuration and authentication failures are not useful to retry every minute. A missing key is
rejected at startup. If OpenRouter rejects an installed key or request configuration, the worker
will retain the submission in `queued`, record a safe diagnostic, and apply a longer operational
retry delay of one hour while logging the error for the tutor/operator. Secrets and full student
payloads must not be stored in `marking_last_error` or logs.

An unexpected process interruption can leave a row in `processing`, as it can today. Recovery of
stale processing claims is outside this change's scope and should be addressed separately if the
deployment requires crash recovery guarantees.

## Data Handling

Submitted student images, OCR text, and published solution images will leave the local machine and
be sent through OpenRouter to a selected free provider. Free providers may log inputs and outputs
or use them for model improvement. This behavior is accepted for the current prototype, but the
application must not claim that automated marking is local or private after this change.

## Testing

Automated tests will use mocked HTTP responses and will never require or transmit a real API key.
Coverage will include:

- correct OpenRouter authentication, endpoint, model, multipart image format, and strict schema;
- OCR and grading response parsing;
- multiple solution images;
- HTTP, rate-limit, timeout, malformed JSON, and schema-validation failures;
- preservation of existing grading invariants;
- due-at selection for queued attempts;
- the exact `3, 10, 30, 30, 60, 60...` retry sequence;
- persistence of retry state across worker invocations;
- clearing retry metadata after success; and
- the one-hour delay for authentication or configuration rejection.

Existing marking, submission, and acceptance tests must continue to pass.

## Operational Result

The bot can process handwriting without a locally installed model. It incurs no inference charge
because it uses `openrouter/free`; in exchange, capacity, latency, model identity, and output
quality may vary between requests. When no compatible free route is available, work stays durable
in PostgreSQL and retries without tutor intervention.
